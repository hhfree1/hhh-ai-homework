这一页的所有截图都来自无头浏览器，不是手工截的。踩了四个坑，每个都值得记下来，因为前三个的表现都是"看起来页面坏了"。

## 坑一：在沙箱里起浏览器，起不来

第一条命令直接崩：

```
FATAL:mojo\public\cpp\platform\platform_channel.cc:187 Check failed: 拒绝访问 (0x5)
```

不是端口被占，也不是参数写错。Chromium 系浏览器的进程间通信在 Windows 上走命名管道，而我当时跑命令的沙箱不允许程序打开命名管道，于是浏览器在初始化阶段就死了。

判断依据是错误出在 `platform_channel`——那是建通道的地方，不是渲染、不是 GPU。换到不受限的环境里跑同一条命令，立刻正常。

## 坑二：后台任务会被一起杀掉

第二个坑更隐蔽。把浏览器放到后台任务里，命令立刻返回、任务状态是 `completed`、退出码 0——看起来一切正常，但 CDP 连不上，因为父进程一退出，浏览器成了孤儿并被清扫。

解决办法不是"让后台任务活着"，而是别让它们分开：在**同一条命令**里依次启动浏览器、跑截图脚本、`Stop-Process` 收尾。三件事绑在一个进程生命周期里，父子关系成立，浏览器就不会被提前收走。

## 坑三：离屏的图片不栅格化

这是最坑的一个。用 `Page.captureScreenshot` 加 `captureBeyondViewport` 一次截整页，出来的图里 `<canvas>` 正常，`<img>` 全是空白。

第一反应是"图片没加载"或者"路径错了"。但写了个小脚本连上 CDP，把所有 `<img>` 的 `naturalWidth / naturalHeight / 布局盒子` 打出来：

```
fig_net.svg        600 × 380   complete  true
fig_loss.svg       720 × 300   complete  true
fig_boundary.png   460 × 460   complete  true
```

图是好的，盒子也正常。问题出在截图方式：超出视口的那部分不会走完整的合成流程，离屏的图片资源没有被光栅化，而 canvas 是自己画的，所以有内容。

换成"滚一段、截一段"（视口截图，不 beyond viewport）之后，四张图全部出现。代价是截一张长图要滚好几次，并且必须等每一段渲染稳定。

## 坑四：入场动画没触发

页面用 `IntersectionObserver` 做入场：元素进入视口才从 `translateY(12px) + opacity 0` 过渡到原位。截图脚本如果直接滚到目标位置，只有那一刻在视口里的元素被触发，其余仍是 `opacity: 0`——截图里就是大片空白。

修法很土：截图前先从头滚到底，再滚回目标位置；或者干脆给截图单独加一个"全部展开"的开关。我选前者，因为它验证的是真实页面，不是特制版本。

## 三个小工具

都走 CDP，没有装 Playwright：

- `shot.mjs`：按 390 / 768 / 1440 三档宽度打开页面，量 `scrollWidth` 与 `clientWidth`（横向滚动）、记下所有非 `file:` 的请求、收集 console 错误，再逐段截图。
- `view.mjs`：滚到指定 y，截一屏视口。排查"这一块到底长什么样"时最常用。
- `diag.mjs`：只打诊断信息，不改样式。上面那段 `<img>` 的输出就是它。

三个脚本加起来不到两百行，够用。

## 顺序很重要

这四个坑排在一条线上，形状是一样的：**先诊断，再改**。

如果坑三那次我按"图片没加载"去改路径，会白改一轮；如果坑四那次我以为是配色问题去调对比度，会白改两轮。真正省时间的动作是加一行输出——`naturalWidth` 是不是 0、`scrollWidth` 是不是大于 `clientWidth`、请求列表里有没有外链。

截图是证据，不是装饰。既然要拿它当证据，就得先确认它拍到的确实是页面，而不是渲染管线的一次意外。
